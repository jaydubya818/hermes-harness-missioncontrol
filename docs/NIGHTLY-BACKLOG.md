## Closed

- [x] 2026-08-24 → 2026-08-24 — A blank `HARNESS_OPERATOR_TOKEN` silently disabled operator auth on all four services — `requireOperator()` opens with `if (!operatorToken) return null;`, so an empty-string value was indistinguishable from an unset one. Unset is the documented local default and correctly means "auth off"; set-but-blank is a deployment that meant to configure auth and got an empty value from an unset shell variable or a missing secret key, and it failed open with no signal. Reproduced on eval-api with `HARNESS_OPERATOR_TOKEN=""`: unauthenticated `GET /api/evals` returned 200 and unauthenticated `POST /api/evals` returned **201**, creating a record; any non-blank token 401s both. The console half already rejected this — `dev:console:auth` uses `${VITE_OPERATOR_TOKEN:?...}`, whose colon form fails on unset *and* empty — so the four backends were the inconsistent side. Each service now calls `assertOperatorTokenUsable()` inside its existing `if (!process.env.VITEST)` startup block and throws before `serve()` when the variable is present but trims to empty. The guard is duplicated per service to match the existing duplication of `requireOperator` and the startup block, rather than introducing a shared auth module (eval-api and worker-runtime do not depend on `shared-types`). Regression tests in all four services, each confirmed failing against the pre-fix source. On `nightly/2026-08-24-improvements`.
- [x] 2026-08-23 → 2026-08-23 — `POST /api/evals` accepted ratio scoring fields above 1 — `confidence`, `efficiency_score` and `risk_score` are documented 0-1 ratios that `summarize()` averages straight into `average_confidence` & co, but the route only checked them for non-negative finiteness. A record posted with `confidence: 500` was stored and the listing reported `average_confidence: 500`, a number no scorer here can produce — `scoreRun()` clamps its own output and `policy-engine` already clamps the worker-reported confidence for exactly this reason. Route now 400s on any of the three above 1; counts and durations stay unbounded. Regression test confirmed failing against the pre-fix source. On `nightly/2026-08-23-improvements`.
- [x] 2026-08-22 → 2026-08-22 — `retry-step` resurrected a cancelled run — `POST /api/runs/:id/retry-step` gated on the step state and accepted `"cancelled"`, so `POST /cancel` followed by `POST /retry-step` returned 200 and flipped `run.status` back to `running`. Cancel is a close-out: it has already recorded the eval and released the worktree and branch, and `/execute-current` refuses cancelled runs outright — retry-step was a one-call bypass. Route now 409s; regression test pins it. On `nightly/2026-08-22-improvements`.
- [x] 2026-08-21 → 2026-08-21 — `@types/node` on the `^24` line against a Node 22 runtime — the types described APIs the pinned runtime lacks, so `tsc` green-lit calls that throw. Pinned to `^22`; verified by a probe using `URLPattern` (a global only from Node 24) that typechecks under `@types/node` 24 and fails under 22.
- [x] 2026-08-21 → 2026-08-21 — Date filter hid records it was never given a range for — `inDateRange()` returned false for a timestampless record even with no `from`/`to`, dropping it from the unfiltered read model. Returns true when neither bound is supplied; regression test pins both halves.
